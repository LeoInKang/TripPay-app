_비공개 테스트 중 수집한 피드백 정리. 정식 출시(프로덕션) 이후 업데이트 반영 예정._

## 1. 유연한 비용 분담 ⭐ 최우선 (테스터 2명 요청)

**현재 동작**: 지출을 참석자 전원에게 1/N(엔빵)으로 균등 분배.

**요청 내용**
- 지출별로 **실제 참여한 사람만** 나누기 (그 지출에 빠진 사람은 제외)
- 1/N 고정이 아니라 **사람별 비율 / 배수 / 직접 금액** 지정
- 위 내용을 모두 반영해 **개인별로 정확히 정산**

**정리(구현 방향)**: 지출마다 `참여자 목록 + 분담 방식(균등 / 비율 / 배수 / 고정액)`을 선택 → 정산 계산에 반영. (Splitwise 스타일)

**원문**
- 테스터 A: "지출도 일부 인원 빠질 수 있으니 참석자만 엔빵이 되면 좋고 … 각 개인별로 정산하게"
- 테스터 B: "비용 부담을 무조건 1/N 말고 사람별 비율 또는 배수 등을 넣어서 할 수 있도록"

---

## 코드 확인 결과 (SettleTab.js)
- **현재 정산 = 남은 잔액 ÷ 인원수(N)**. `refundPer = totalBalKrw / N` → 모든 참석자에게 **동일 금액** 표시.
- **개인별 회비 납부액을 계산에 전혀 사용하지 않음** → 불균등 회비가 정산에 **반영 안 됨** (많이 낸 사람도 똑같이 환급).
- 지출은 전원 공동 부담 가정 → **지출별 참여자 개념 없음**.
- 회비 입력 자체는 사람별·건별 다른 금액 가능하나, **정산이 이를 무시**함.

## 개선 방향 (핵심)
정산을 **개인별 순액 방식**으로 재설계:
`개인 환급/부담 = (본인이 낸 돈: 회비·충전 등) − (본인 몫 지출)`
- 지출마다 `참여자 + 분담 방식(균등/비율/배수/고정액)` 지정 → 개인 몫 계산
- 개인별 낸 돈 합계 반영 → 많이 낸 사람이 더 돌려받도록

### 선결제/대납 처리 방침 (기능 아님, 운영 가이드)
원칙 하나: **대납액은 장부에 딱 한 번만 나타나야 한다.** 상황별 처리는 세 가지.

① **공금이 넉넉함 (기본)** — 입금 기록 없음.
   지출 1건 기록(참여자 = 실제 그 비용을 쓴 사람들) + 공금에서 대납자에게 지불. 대납자는 본전.
② **공금 부족** — 전원 **균등 추가 회비 징수**(입금 기록) → 지불 + 지출 1건 기록.
③ **정산까지 안 갚음** — 대납액을 **그 사람의 회비**로 기록 + 지출 1건 기록 → 순액에서 자동으로 돌려받음.

- **입금과 부담은 독립이다.** 지출의 참여자·분담방식은 ①②③ 공통으로 실제 사용 기준(균등일 필요 없음). 회비를 누가 얼마 냈는지는 부담과 무관하고, 그 차이는 순액 정산이 자동으로 상쇄한다 — ②의 "균등 징수"도 공정성 장치가 아니라 걷기 편한 방식일 뿐이다.
- 지출의 결제수단은 대납자가 뭘로 냈는지가 아니라 **공금이 실제로 어떻게 나갔는지**로 적는다(계좌이체 갚음 = 원화 지출, 현지 현금 갚음 = 외화 지출·현금). 잔액 3종이 실제와 맞으려면 이게 기준.
- 대납이 반복돼 불편하다는 피드백이 쌓이면 "결제자 필드" 기능화 재검토 (순액 = 회비 + 대납액 − 부담. 잔액 계산에서 대납 지출 제외 + 갚음 처리 상태 전이가 필요해서 SplitEditor급 작업).

**⚠️ 개인 카드로 결제한 대납을 "카드 지출 + 충전" 짝으로 적지 말 것.**
앱의 계좌·카드·현금은 전부 총무의 공금 지갑이다. 공용 카드에 일어나지 않은 일을 기록하면
카드 이력이 오염될 뿐 아니라, **가짜 충전이 평균환율(getAvgRate)에 들어가 전원의 환산 금액을
미세하게 틀어놓는다.** 개인 카드 대납은 위 ①②③의 원화 경로로만 처리한다.
충전 기록이 정당한 경우는 **공용 카드에 실제로 돈이 들어갔을 때뿐**이다.

**충전·환전을 개인 돈으로 대납한 경우** (공용 카드에 실제 충전이 일어났고, 자금만 개인 돈인 케이스)
- 충전 기록은 이미 "계좌에서 나간 것"으로 잡혀 있다는 게 핵심.
- **정산 전에 갚으면** → 공금 계좌에서 송금만 하고 **아무것도 추가 기록하지 않는다.** 충전 기록이 곧 그 차감이므로, 지출로 또 적으면 이중차감.
- **안 갚고 정산까지 가면** → 대납액을 그 사람의 **원화 회비 1건**으로 기록(메모: 충전 대납). 낸 돈이 늘어 순액에 자동 반영되고, 계좌 잔액도 실제와 일치하게 된다.
- 메모("지급필요")는 운영용 표시일 뿐 정산 엔진은 읽지 않는다.

### 지출 일부만 공금 부담 (기능 아님, 운영 가이드)
- 상황: 지출 한 건에서 **일부는 특정 인원만, 나머지는 공금**이 부담하게 하고 싶을 때.
- 전제: 공금은 별도 지갑이 아니라 참석자들이 낸 회비다 → **"공금 부담" = "전원 균등 부담"**. 별도 개념이 필요 없다.
- 방법: **지출을 두 건으로 나눠 입력**한다.
  - `골프 그린피 60,000` — 참여자 A·B
  - `골프 공용비 40,000` — 참여자 전원
  - 결과(A·B 부담 40,000 / C·D 부담 10,000)는 한 건에 고정액으로 직접 넣은 것과 **완전히 동일**. 계산이 필요 없고 내역에 근거가 남는다.
- 한 건 안에서 "일부만 개인 부담"은 지원하지 않는다. 부담 합계 < 지출액이면 공금에서 나간 돈이 아무에게도 안 잡혀 정산 총합이 실제 잔액과 어긋나기 때문. 고정액 저장 시 `checkFixedSplit`이 막는다.
- SplitEditor 안내 문구에 이 방법을 적어 뒀다.

## 2026-08-04 수정 (정산 정확도)
- **평균환율 단일 출처화** — `settle.js`의 `getAvgRate(trip, charges, exchanges)`를 Home·Settle·Deposit 세 탭이 함께 쓴다. 실거래(충전·환전) 0건이면 `country.exRate`로 폴백.
  - 고친 문제 ①: 현황 탭은 저장된 `krwEquiv`, 정산 탭은 현재 평균환율을 써서 **외화 회비가 있으면 두 탭의 '총 입금'이 달랐다.**
  - 고친 문제 ②: 충전·환전이 0건인 여행(환전 없이 외화 현금만 걷은 경우)에서 정산 쪽 환율이 0이 되어 **외화 회비가 0원으로 잡히고 순액이 뒤집혔다.**
  - 현황 탭 '총 지출'도 정산 탭과 같은 건별 환산 후 합으로 통일.
- **분담 합계 검증 — 고정액·비율 공통 규칙으로 통일.** `splitErrorMessage`가 저장을 막는다(지출 추가 2곳 + 내역 수정 모달). 접힌 편집기 헤드에도 부족·초과 배지 표시.
  - 고정액(`checkFixedSplit`): 합계 = 지출액. 보정이 없어 어긋나면 공금에서 나간 돈이 아무에게도 안 잡힌다.
  - 비율(`checkRatioSplit`): 합계 = 100%. 엔진이 총 가중치로 정규화해서 **계산은 원래도 맞았지만**, 30/30/30을 넣으면 각자 33.3%를 물어 **입력값과 실제가 달랐다.** 세 모드 중 유일하게 어긋나던 지점이라 고정액과 같은 규칙으로 맞췄다.
  - **'100%로 맞추기' 버튼**(`normalizeRatio`) — 비를 유지한 채 합계를 정확히 100으로 정규화. 2:1:1 → 50/25/25, 1:1:1 → 33.34/33.33/33.33. 100% 강제로 잃는 배수 입력을 이 버튼으로 되살렸다(엔진의 `shares` 모드는 여전히 UI 미노출).
  - 비율 각 행에 실제 부담 금액을 함께 표시.
  - 엔진(`settle.js`)의 계산 로직은 그대로다. UI 제약만 추가한 것이라 기존 데이터의 정산 결과는 안 바뀐다.
  - ※ 이미 어긋나게 저장된 기존 지출은 자동으로 고쳐지지 않는다. 해당 지출을 수정할 때 차단되며 드러난다.
- 단위 테스트 20 → **54개**(`node test-settle.mjs`).

### 영수증 자동입력 (v1.2 후보 · 2026-08-05 실증)
- 실증: 실제 여행 영수증 20장(렌터카 정산서·골프장·마트·식당·주차·숙박)을 Claude에 올려 파싱 →
  가져오기 JSON 생성 → 앱 가져오기. **확인 질문 1개(골프장 영수증이 1인분인지 합계인지), 수정 0건.**
- 현재 워크플로우: 사진 → Claude(코워크) → JSON 파일 → AirDrop → 앱 "여행 데이터 가져오기".
- **모델 중립**: 프롬프트 템플릿 `docs/receipt-import-prompt.md` — ChatGPT·제미나이에 붙여넣어도 같은 JSON이 나온다. v1.2에서는 워커의 업로더 페이지(`/upload`: 붙여넣기 → 클라이언트 암호화 → QR)로 어떤 AI든 동일 UX.
- **프롬프트 복사 UI는 v5.1에서 제외** (2026-08-06): 수동 경로(복사→AI→파일→AirDrop→가져오기)가 일반 사용자에겐 과하게 번거롭다는 판단. 코드·의존성(expo-clipboard) 제거 완료. 사용자용 영수증 입력은 v1.2 링크 방식으로 처음 공개한다.
- v1.2 구상: **"링크로 가져오기"** — AI가 지출 목록을 암호화해 공유 워커에 올리면 `…/i/<id>#키` 링크 하나가 나온다.
  기존 워커·AES-GCM을 역방향으로 재사용. 수신은 같은 링크를 세 가지 길로:
  ① **같은 폰**(주 사용례 — 영수증을 찍는 기기가 폰이니 AI도 폰에서 쓴다): 링크 탭 → 딥링크로 앱이 직접 수신.
     폴백은 앱 가져오기 화면의 "링크 붙여넣기".
  ② **다른 기기**(Mac 코워크 ↔ 폰): 화면의 QR을 폰으로 스캔.
  ③ **예외**: 짧은 코드 입력(암호 강도가 낮아지는 트레이드오프, 최후 수단).
  앱은 수신 후 **대상 여행 선택 → 미리보기 → 추가** 순서로:
  - 대상 여행 선택: 기본 = 마지막 사용 여행, 통화 일치 여행 우선 정렬. 맞는 여행이 없으면
    번들의 여행 메타(이름·기간·국가)로 **새 여행 생성**을 제안.
  - 미리보기: N건·합계 표시, 통화 불일치 경고, batchId로 같은 묶음 재추가 차단.
  - 확정 시 지출 id는 앱이 재발급해 append(기존 지출과 충돌 방지) → 자동 저장 → 정산 반영.
- **앱 내장 비전(카메라→API 파싱)은 무료 배포와 상성이 나쁘다** — 링크 방식 다음 단계로만.
  - 품질 자체는 문제없다: 파싱 주체가 같은 LLM 비전이라 2026-08-05 실증과 동일. 단, 대화형 질문이
    불가능하므로 모델이 확신도를 함께 반환하고 앱이 **미리보기 폼에서 불확실 필드를 표시**하는 설계가 필요
    (전통 OCR·영수증 특화 파서는 렌터카 정산서의 예정/정산/예치금 구분, "받은 돈 vs 합계" 같은 판단을 못 한다).
  - 비용: 장당 ~5원(Haiku급)~15원(Sonnet급). 사용자가 늘수록 상한 없이 커지고, 공개 프록시라
